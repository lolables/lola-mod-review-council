# Review Council — Developer Guide

Source for the `review-council` Lola module. All changes go in `./module/`;
never edit an installed copy (`~/.claude/skills/review-council/`,
`~/.config/opencode/skills/review-council/`) — install overwrites it.
`module/AGENTS.md` is injected into users' AGENTS.md by lola: keep it
host-agnostic.

## Commands

- `task test` runs unit suites only; `task check` is lint + the full matrix.
- Lint with `task lint`, never bare `shellcheck` — it misses what the gate rejects.
- `RC-NNN` guard IDs are one namespace across `module/tests/` and
  `.taskfiles/scripts/mutate-check.sh`. Take the next free one from
  `grep -rhoE 'RC-[0-9]{3}' module .taskfiles | sort -u | tail -1`, never
  from one directory alone.
- `task lola-eval:update` before eval runs: the harness floats on upstream
  `main`, but an existing `.venv` stays on the commit it first installed.

## Testing: token-conservative by default

- Default to the lightest check that proves the change: `bash -n`, a jq
  smoke run, or one test file, filtered to failures:
  `bash .taskfiles/scripts/with-scratch.sh bash module/tests/<file>.sh 2>&1 | grep -E '^ *FAIL|^Results:' | head -20`.
  Never run a test file bare: mock clones land in the real `~/.cache`.
- Never paste a suite's full output into context, and don't re-run a green
  file to double-check.
- Heavy runs need explicit user approval first: `task check`, `task lint`,
  `task test` / `test:all` / `test:mutate` / `test:e2e`, more than one test
  file at a time, and any `lola-eval` or live review run. Otherwise, write the
  tests and hand the user the commands.
- Never let a test depend on `find`/glob/readdir order. Local filesystems
  here return creation order, so it passes locally; CI (ext4, APFS) does not.
- Before a live review run, read "Live trials" in `docs/dev/testing.md`.

## Files that change together

- `rc-prepare.sh` flags ↔ SKILL.md Step 0 table. `--help` is truth for valid
  flags; SKILL.md is truth for mapping intent to them. A new routing path needs
  an eval case whose followup requests `FLAGS_PASSED` and `SCOPE_USED`.
- `review-council/SKILL.md` → check `review-council-debug/SKILL.md` for new
  edge cases (status handling, flags, output fields).
- `verdict-schema.json` ↔ `reviewer-protocol.md` worked examples ↔ fixtures in
  `test-verdict-schema.sh` / `test-rc-extract-verdict.sh`. Changing what
  `rc-verify-evidence.sh` reads → recheck `phases/verify.md` "Interpreting
  Evidence Check Results".
- `agents/review-council-arbiter.md` (calibration rules, reply example) ↔
  `validation-schema.json` ↔ `scripts/jq/apply-validation.jq`. RC-105 runs the
  reply example through the jq program; RC-058/059/128/129 pin the rules there.
- `pr-conversation.txt` envelope in `scripts/lib/prepare-context.sh`
  (delimiters, `Author:`/`Timestamp:`/`Body:`, column-0 anchoring) ↔ the
  "Column 0 is the entire trust boundary" paragraph in `disposition.md`'s
  Step 3 prompt ↔ `case-022`–`case-025` and `case-027` fixtures.

- `module/skills/review-council/VERSION` stamp format (`X.Y.Z`, `X.Y.Z+dev`)
  ↔ `.taskfiles/scripts/release-bump.sh` (writes it) ↔
  `module/skills/review-council/scripts/lib/council-version.sh` (reads it, for
  the report header and the batch driver's plan) ↔ the table in
  `docs/dev/releasing.md`.

## Changelog and releases

`CHANGELOG.md` is generated by git-cliff from Conventional Commit subjects —
never edit it. Write commit subjects as release-note lines. Releases are cut
with `task release:bump`; see `docs/dev/releasing.md`.

## Module markdown style

Markdown under `module/` is compressed "caveman" style: drop articles and
filler, keep fragments; preserve technical terms, code, paths and
output-template strings verbatim. Match it when editing. Do NOT compress
script-emitted report content, `CHANGELOG.md`, `README.md`, this file, or
anything in code fences/backticks.

`SKILL.md` and `phases/*.md` are loaded whole by the host: never split them or
move content out to a linked file, even when a docs audit flags them. That
applies to `README.md` and `docs/` only.

## Forge output

Anything posted to a forge (PR/MR comments) must not reveal the run's security
posture: sandboxing, which guards ran, where enforcement falls back to prose.
That goes to `tracking.md`, `report.md` or stderr. Verdict and coverage
disclosures (skipped reviewers, trimmed comments, validation mode) stay public.

## Personas

Five: guard, adversary, testing, sre, curator. Architect, Scribe, Herald and
Envoy were removed — update any reference to them you find.

`module/agents/review-council-arbiter.md` is not a persona: it calibrates and
validates verified findings (`verify.md` Step 4). Never give it a `divisor-`
name — that prefix is the persona discovery glob.

## Eval cases (`.lola-eval/tests/`)

- Every case exercises SKILL.md Step 0 routing; no bare `/review-council`
  prompt — case-003 is the sole control. Disposition cases (022–025, 027)
  seed a prior session instead.
- Every rubric scores `no_flapping`: the agent grepping for, re-reading, or
  path-guessing instruction files instead of loading each once.
- Cases needing history beyond the starter commit ship a `scaffold.sh` beside
  `prompt.md`/`rubric.md`/`task.yaml` (not in `starter/`). The external harness
  runs it with the workdir as `$1`, after `reset.sh` makes the "starter"
  commit. It must be idempotent, exit non-zero to abort, and commit with
  `git -c user.name="scaffold" -c user.email="scaffold@test"`.

## A/B evaluations

Before measuring whether a tool or module change makes reviews cheaper or
better, read `docs/dev/ab-evaluations.md`. Its rules are what the code-graph and
context-mode runs cost to learn.
